-------------------------------------------------------------------------------
KOMUT ([KALIP-1] birebir):

BEKLENEN:
  - İlk satır: HTTP:200   (LoginController HttpStatus.OK döner, 201 DEĞİL)
  - Son satır: "<sayi> target/jwt_admin.token" ve <sayi> 150-300 arasında olmalı
    (ÖLÇÜLDÜ, tahmin değil: 185 = JWT 184 bayt + sondaki newline; .env'deki üretim
    anahtarıyla, yani HS384 imzayla). 0 veya 1 çıkarsa python3 token'ı yazamamıştır.
  - python3 traceback'i (KeyError: 'object' gibi) geldiyse login başarısızdır -> [ON_ERROR].

Cevap gövdesini gör:
  wsl -e bash -lc 'cd /mnt/c/angularAndJava/on_muhasebe/on-muhasebe-spring-boot && cat target/login_admin.json; echo'
BEKLENEN: "success":true ve "object" içinde "jwtToken" alanı bulunmalı, ör:
  {"success":true,"object":{"jwtToken":"eyJhbGciOiJIUzM4NCJ9...."}}
Alan sırası önemli değil; "success":false veya "message" alanı geldiyse -> [ON_ERROR].
İmza algoritması jwt.secret'ın çözülmüş uzunluğuna göre seçilir (>=384 bit -> HS384,
256-383 bit -> HS256). .env'deki üretim anahtarı 384 bit olduğu için header HS384'tür;
src/test/resources'taki test anahtarı 288 bit olduğundan orada HS256 görürsün. Bu bir
kriter DEĞİLDİR, sadece header'ı görünce şaşırma diye yazıldı.

-------------------------------------------------------------------------------
LOGIN.2  TOKEN İÇERİĞİ DB İLE TUTARLI MI (payload decode)
-------------------------------------------------------------------------------
Token'ın imzasını doğrulamıyoruz (secret bizde yok, gerek de yok: imzayı zaten
uygulamanın kendisi modül 2'de her istekte doğrulayacak). Burada payload'ı okuyup
claim'leri DB ile karşılaştırıyoruz.

KOMUT:
  wsl -e bash -lc 'cd /mnt/c/angularAndJava/on_muhasebe/on-muhasebe-spring-boot && python3 -c "import base64,json;t=open(\"target/jwt_admin.token\").read().strip();parcalar=t.split(\".\");p=parcalar[1];p+=\"=\"*(-len(p)%4);c=json.loads(base64.urlsafe_b64decode(p));print(\"parca=\"+str(len(parcalar)),\"sub=\"+str(c[\"sub\"]),\"userId=\"+str(c[\"userId\"]),\"adminId=\"+str(c[\"adminId\"]),\"gun=\"+str((c[\"exp\"]-c[\"iat\"])//86400))"'

BEKLENEN (tek satır):
  parca=3 sub=bozlak userId=1 adminId=1 gun=30

  parca=3   : JWT üç parçalıdır (header.payload.signature). Farklıysa dosyaya token
              yerine başka bir şey yazılmıştır.
  sub       : JwtServiceImpl.buildToken -> JwtClaimsSet.builder().subject(userDetails.getUsername())
  userId=1  : LoginServiceImpl extraClaims'e userId koyar.
  adminId=1 : Kullanıcı admin OLMASAYDI bu değer -1 olurdu. -1 geliyorsa bozlak admin
              sayılmamış demektir -> [ON_ERROR] (modül 2'deki add-user 403 verirdi).
  gun=30    : JwtServiceImpl.TOKEN_VALIDITY -> Duration.ofDays(30). Farklı bir sayı JWT
              ömrünün değiştiği anlamına gelir; testin geri kalanını etkilemez ama
              sessizce geçme, [ON_ERROR] ile bana bildir.

DB DOĞRULAMA (claim'ler DB ile birebir aynı mı):
  wsl -e bash -lc 'docker exec pre_accounting_db psql -U bozlak -d test_db -tAc "SELECT u.user_id, a.admin_id FROM users u JOIN admins a ON a.user_id = u.user_id WHERE u.username = '\''bozlak'\'';"'
BEKLENEN: 1|1        (psql -tA sütunları | ile ayırır, ilk alan user_id, ikincisi admin_id)
Bu çıktı, üstteki komutun userId ve adminId değerleriyle AYNI olmalı. Tutmuyorsa
-> [ON_ERROR]; sonraki bütün modüller yanlış kullanıcının adına iş yapar.
